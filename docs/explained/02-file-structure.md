# File structure, and why it's shaped this way

## The tree

```
lora-relevance-classifier/
├── pyproject.toml              hatchling build, torch/transformers/peft/datasets, ruff/mypy/pytest config
├── README.md
├── notebooks/
│   └── train_on_colab.md       the exact commands for the real GPU run, written before it happened
├── src/lora_relevance_classifier/
│   ├── __init__.py
│   ├── dataset.py              SourceQuestion, PairExample, build_pairs(), split_pairs() -- pure logic
│   ├── build_dataset.py        CLI: reads rag-qa-api's dataset.jsonl, writes data/{train,val}.jsonl
│   ├── config.py               LoraSettings, TrainConfig -- plain dataclasses
│   ├── metrics.py              ClassificationMetrics, compute_metrics() -- pure, no model needed
│   ├── baseline.py             word_overlap_score()/word_overlap_predict() -- the zero-training baseline
│   ├── train.py                build_model_and_tokenizer(), train() -- the real LoRA fine-tune (needs torch/peft)
│   ├── evaluate.py             predict(), evaluate_pairs(), load_base_model(), load_adapter_model()
│   └── cli.py                  `lora-relevance-classifier train`, `lora-relevance-classifier compare`
├── tests/
│   ├── test_dataset.py          pairing/splitting logic, no model
│   ├── test_metrics.py          metric math, no model
│   ├── test_baseline.py         word-overlap logic, no model
│   ├── test_config.py           dataclass defaults/overrides, no model
│   ├── test_build_dataset.py    the CLI script, no model
│   ├── test_cli.py              argument parsing + the baseline-only path of `compare`
│   └── test_train_smoke.py      the ONE test that loads and fine-tunes a real (tiny) model
├── data/                        generated by build_dataset.py; gitignored (derived from rag-qa-api's data)
└── .github/workflows/ci.yml
```

## Why `dataset.py`/`metrics.py`/`baseline.py` have zero dependency on torch/transformers

Every file in that list is plain Python (`json`, `random`, `re`, `dataclasses` -- nothing
else). This is what lets 18 of the 22 tests run in milliseconds, with no model download, no
GPU, and no risk of a flaky HuggingFace Hub request failing an unrelated test. Only
`train.py`, `evaluate.py` and the one test that exercises them (`test_train_smoke.py`) touch
the actual ML stack -- the split is the same reasoning as `llmtrace`'s pricing/extractors vs.
storage split, or `agent-loop`'s tool logic vs. MCP wiring split: isolate the part that can be
tested fast and deterministically from the part that genuinely needs the heavier dependency.

## Why `build_dataset.py` is a separate script from `train.py`/`cli.py`'s `train` subcommand

Building the dataset needs `rag-qa-api`'s `evals/dataset.jsonl` as input but nothing from the
ML stack; running it doesn't require `torch` to even be importable. Keeping it as its own
entry point (`python -m lora_relevance_classifier.build_dataset`) rather than a `lora-relevance-classifier` CLI
subcommand means someone could, in principle, generate the dataset in an environment that
doesn't have `torch` installed at all (e.g. a lightweight CI step, or a laptop before uploading
data to Colab) -- `cli.py` only defers its own `torch`/`transformers` imports until `train`/
`compare --adapter-dir` actually need them, for the same reason (see `04-code-and-logic.md`).

## Why `data/` is generated, not checked in

`data/train.jsonl`/`data/val.jsonl` are a deterministic function of `rag-qa-api`'s
`evals/dataset.jsonl` plus `build_pairs`'s `seed` parameter -- regenerating them is one command
(`python -m lora_relevance_classifier.build_dataset --source ...`), and committing a derived artifact
alongside the script that derives it invites them silently drifting apart (the script changes,
the committed file doesn't get regenerated, and the two no longer agree). `.gitignore` excludes
`data/*.jsonl` for this reason, the same way `rag-qa-api`'s own generated chunks table isn't a
checked-in file either.
